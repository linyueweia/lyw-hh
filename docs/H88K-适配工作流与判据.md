# H88K（Hinlink V3 / RK3588）适配工作流与判据

本文只写**在真机上量到的东西**和由此得出的判据。所有实机数据来自用户设备 `192.168.10.90`
（iNextOS 26.2.1 / 内核 `6.1.115-vendor-rk35xx`），2026-10-17 采集。

---

## 0. 硬件事实（不可改的部分）

```
eth0 = 0004:41:00.0      r8125（RTL8125）  2.5G     PCIe
eth1 = 0003:31:00.0      r8125（RTL8125）  2.5G     PCIe
eth2 = fe1b0000.ethernet st_gmac + RTL8211F 千兆    平台 GMAC
```

- 两颗 RTL8125 都**没有出厂 MAC**（dmesg：`Invalid ether addr 00:00:00:00:00:00` → 每次开机随机 MAC）。
  这也是 roceos 里按 MAC 做绑定时会"自己变"的原因；目前不改（要改需 systemd `.link` + 稳定 machine-id）。
- 内核配置（`/boot/config-6.1.115-vendor-rk35xx` 实测）：
  `STMMAC_ETH=y`、`DWMAC_ROCKCHIP=y`、`R8125=m`、`R8169=m`、`LEDS_GPIO=y`、
  `LEDS_TRIGGER_NETDEV=y`、`LEDS_TRIGGER_HEARTBEAT=y`、`BLK_DEV_NVME=y`、
  `SATA_AHCI_PLATFORM=y`、`PCIE_DW_PLAT_HOST=y`。
- `/boot/dtb/rockchip/rk3588-hinlink-h88k.dtb`；`cma=256M` —— 与官方 `iNextOSA_26.2.1_Easepi-r2` 的 `armbianEnv.txt`（`extraargs=cma=256M`）一致，本仓不改这个值，只断言。

## 1. 口序反了（ETH0 ↔ ETH2）

**现象**：官方镜像刷完，用户插"ETH0"其实是系统里的 `eth2`。

**根因链**（读镜像 + 读运行系统确认）：
1. 上游 `config/boards/hinlink-h88k.csc` 里**没有任何网口代码**，只有音频 udev 重命名。
2. 官方镜像靠 `/usr/local/sbin/gen-eth-order.sh` 在开机时"猜"口序：SoC 平台口优先、PCIe 口按字典序。
   实测结果是 `fe1b0000`（千兆）被排到第一位，两个 2.5G 口挤到后面 → 用户看到的"反了"。
3. 真正改名的是 `/usr/lib/istorenext/fix-ifaces-name`（`fix-ifaces-name.service`，
   `Before=network-pre.target`），它**只读 `/etc/eth_order`**。

**修法**：把 `/etc/eth_order` 钉死成实机口径 —— 板级 csc 里 `post_family_tweaks__lyw_hh_h88k_static_eth_order`。

```
0004:41:00.0,0003:31:00.0,fe1b0000.ethernet
```

**附带需求"插千兆口一定能进后台"**：`istorenext-init-network` 首次开箱时，
若无 `/root/.default-network` 就取**编号最大的 ethN**（= eth2 = 千兆口）并给 `192.168.100.1`，
然后把该文件删掉。所以只要口序对，这个需求天然成立 —— 反过来说，口序错的时候它就会把后台
放到 2.5G 口上，用户自然"插千兆口进不去"。判据 `net-pin-check.py` 会同时查 `.default-network`
（若存在且不是 eth2 即红）。

## 2. 后台登录即退出（roceos JWT 一签发就过期）

**现象**：进 `http://<ip>/` 登录成功，界面闪一下就回登录页。

**取证**：
```
系统时间 Wed Aug 26 10:22 UTC 2026     ← 比真实时间早 7 周
RTC      Sat 2026-10-17T10:10:17 UTC   ← 硬件时间是对的
/etc/fake-hwclock.data = 2026-08-26 10:03:33   ← 构建日期
```
`fake-hwclock-load.service` 开机把 `.data` 写进系统时间（覆盖 RTC）。roceos 用 `jwt.expire_hours: 24`
签发 token，前端每 30 s 比较 `exp` 与本地时间 → 恒为负 → 立刻 logout。

**修法**：`ln -sf /dev/null /etc/systemd/system/fake-hwclock-load.service`（systemd mask 语义）、
`.data` 写构建时刻、镜像自带 `systemd-timesyncd` 时确保开机启动。

**判据**：`verify-image.sh` 断言 mask 链接指向 `/dev/null`、`.data` 不早于 `2026-09-01`（回退即红）。

## 3. 前面板系统灯不亮

**取证**（`/proc/device-tree/leds/`）：
```
leds/net   gpios=(phandle 0x1a3, gpio 19)   无 linux,default-trigger
leds/sata  gpios=(…, gpio 21)               无 linux,default-trigger
leds/user  gpios=(…, gpio 15)               无 linux,default-trigger
leds/work  gpios=(…, gpio 57)               default-trigger=default-on   ← 唯一亮的一颗
```
`ls /sys/class/leds` 四颗都在，但前三颗 trigger 停在 `none`、brightness=0，用户态没人管 → 一直灭。
**DTS 本身没问题、不需要改**（用户确认过）：它把四颗灯的 GPIO/标注都描述对了，只是没写
`linux,default-trigger`——这属于"运行期由谁驱动灯"的选择，本来就该由用户态决定。

**修法（用户态，不动 DTS）**：`h88k-admin-ip.sh`（systemd `h88k-admin-ip.service`，20 s 循环）：
```
blue:net   → netdev，绑 br-lan1（桥还没建时先绑 eth0；link/rx/tx 全开）
green:user → heartbeat
amber:sata → disk-activity
red:work   → 保持 DTS 的 default-on
```
为什么不用 DTS 补：`linux,default-trigger = "netdev"` 在 DTS 里无法指定"绑哪张网卡"，
而我们要的是"整个 LAN 桥谁有流量都闪"，只有用户态能做到（`device_name` 可写 br-lan1）。

**实测**：绑 br-lan1 后 `link=1 rx=1 tx=1`，ping LAN 设备时 `brightness` 在 1/0 间交替。

## 4. roceos-ai 每 5 秒崩一次

**取证**：`/opt/roceos-ai` 只有 `librkllmrt.so` + `server.py`，unit 里
`RKLLM_CONFIG=/opt/roceos-ai/model.conf` 指向的文件不存在 → `Restart=on-failure` 无限重启
（实机 `NRestarts=206`）。

**官方对照（实测镜像 `iNextOSA_26.2.1_Easepi-r2_trixie_vendor_6.1.115_minimal.img`）**：
官方同样不带模型文件 —— 区别只在两处：

```
/opt/roceos-ai/server.py:  sys.exit(1)  →  sys.exit(3)   （缺模型时）
/etc/systemd/system/roceos-ai.service:      + RestartPreventExitStatus=3
                                            - Wants=roceos.service
```
unit 原文注释："server.py 在未下载模型时以 3 退出，此时重启没有意义；下载完成后由后端主动 start"。

**修法**：采用官方那两份文件（本仓 `files/roceos-ai/`，sha256 钉死并覆盖载荷版本）。
实机验证：`ExecMainStatus=3`、`NRestarts=0`，不再每 5 秒崩溃。
真正启用推理：放好 `.rkllm` → `model.conf` 写一行模型绝对路径 → `systemctl start roceos-ai`。

## 5. 网口灯（RJ45）—— 不是故障，别再修

同一根线、同一个对端，实测：

| 口 | 速率 | 灯 |
|----|------|-----|
| eth0（2.5G / RTL8125） | 2500 | 亮 |
| eth1（2.5G / RTL8125） | 1000 | 亮（用户实测） |
| eth1（2.5G / RTL8125） | 100 | 灭 |
| eth2（千兆 / RTL8211F） | 100 | 亮 |

结论：**2.5G 口的灯表示"链路 ≥1G"，千兆口任意速率都亮**。差异来自 PHY 的 LED 配置
（千兆口另有一段内核厂商修正 `phy_rtl8211f_led_fixup in val=0x0a42`）。
`r8125` 驱动不开放 LED 开关（无模块参数、无 sysfs、`SIOCGMIIREG` 全 0）→ 软件无法改。

**另有一条同源事实**：对端若只通告 10/100，插哪个口都只能 100M —— 与口无关。

## 6. 判据单点化（防"最后一分钟才红"）+ 布局自适应

lyw-rr 的教训：`verify-image.sh` 里硬编码 `grep 'lan2=eth2'` 与已变更的口径打架，
4.7 GB 镜像全部断言绿、只最后一行红，117 分钟白跑。

本仓口径只定义一次：**板级 csc 里的 `LYW_HH_ETH_ORDER`**（`tools/net-pin-check.py` 里不抄地址）。

- `--src <csc>`：构建前查仓库默认值（外加 `KERNEL_TARGET=vendor`、DTB、钩子存在、字面量只出现一次）
- `--conf <rootfs> [--src <csc>]`：构建后查镜像内 `/etc/eth_order` 与 `.default-network`，
  给了 `--src` 就**逐字等于** csc 声明（口径单点）
- `tools/tests/net-pin-check-test.sh`：16 例负例自测（空/两口/千兆排首/互换/重复/地址写错/USB 网卡/
  默认口写错/KERNEL_TARGET 非 vendor/钩子缺失/字面量被抄第二份 …），判据本身必须能红。

**布局自适应**（lyw-hh run #6 的教训）：本板 csc 没有 `BOOTFS_TYPE`，产物是**单分区**
（`p1 = rootfs(ext4)`，引导文件在 rootfs 的 `/boot`，与官方 H88K 镜像同构）；
写死「`p1=bootfs` / `p2=rootfs`」就会在单分区镜像上第一行 `exit 1`，一条断言都不跑
（那次镜像已编好、artifact 也已上传，但自证等于没做）。
现在：枚举 `pN` → `blkid` 取 `TYPE`/`PARTLABEL` → 认定 `rootfs`（GPT 名优先，其次最大的可挂载分区）
与 `bootfs`（vfat/msdos），bootdir 回落 `<rootfs>/boot`；挂上的分区缺 `/etc` `/usr` 就**响亮失败**
并打印分区表，绝不输出一屏假断言。
`tools/tests/layout-probe-test.sh` 用 4 个微型镜像（单分区 / 双分区 / 不像 rootfs / 随机字节）
在**构建前**秒级验证这套探测。

CI 里三处都跑：早期 lint（网口口径 + 16 例负例）、布局探测自测、构建后 `verify-image.sh`。

## 7. 与实机的对应关系

本仓 `adapted` 产物 = 用户实机现状的最小可重现集合：

| 实机做法 | 本仓实现 |
|---|---|
| `/etc/eth_order` 静态三口 | csc 钩子写入 |
| `fake-hwclock-load` mask + `.data` 更新 | `lyw-hh-clock.sh` |
| `h88k-admin-ip.service`（地址 + 灯 + 桥跟随） | `lyw-hh-net.sh` |
| `roceos-ai` 停用（当时用 `ExecStart=/bin/true` 临时处理） | 改为 `ConditionPathExists`（更干净，模型补上即生效） |

| 内核符号（R8125/STMMAC/DWMAC/LEDS_*） | 不动（厂商树默认值，不入判据） |

## 8. 包集合口径（2026-10-31 定案：与官方 minimal 逐包对齐）

- 判据单点 = `tools/packages-parity-check.py`；`verify-image.sh` 只负责调它。
- 旧写法（把 `packages.additional` 整份当黑名单、成员出现即红）在 run #26 打出 15 条假红。
  那 15 个包在官方 minimal 里本来就都有，来源是：框架三层 base 清单

  `istorenext.sh` 的 `add_packages_to_image`、两者的 Depends/Recommends 传递、apt `Auto-Installed`。

## roceos 载荷怎么跟官方版本（2026-10-31 定案）

**一句话**：roceos 是 iNextOS 的网页后台，**不在 armbian-easepi 框架里**，它有自己的在线升级通道；
固件镜像里打进去的版本必然落后于线上最新版（实证：官方 A2 2.9.1 固件镜像内 `roceos` 是 2.9.x，
而同一台实机 OTA 后已经是 **3.0.2**）。所以「跟官方」要跟的是更新服务器，不是镜像。

### 官方更新地址（不是文档抄的，是从 roceos 二进制里取的常量）

```
GET http://update.roceos.com:14380/api/v1/updates/check?version=<当前>&channel=stable_arm&arch=arm64
⇒ {"up_to_date":false,"latest":{"version":"3.0.2","channel":"stable_arm","type":"app",
     "filename":"roceos-v3.0.2-arm64.tar.gz","sha256":"a997a2f8…","size":60458760,
     "released_at":"2026-10-30T14:44:09+08:00","changelog":"…"}}
```

- **channel 必须是 `stable_arm`**：用 `stable` 查会拿到 `roceos-v3.0.2-x86_64.tar.gz`（x86 包）。
- 设备侧显示「稳定版」，`/opt/roceos/version.json` = `{"version":"3.0.2","channel":"稳定版"}`。
- 快捷自查：`python3 tools/check-roceos.py --pinned official-roceos.txt`（rc=1 表示落后）。
- CI：`.github/workflows/build.yml` 的 `roceos` job 每天 03:00 CST 跑同一个脚本并**自动跟版**
  （重建载荷 → 发本仓 release → 改两处 pin → 推送）；落后不再只是红，除非跟版本身失败。
  pin 只存两处：`official-roceos.txt`（真源）+ 扩展里的 `ROCEOS_PAYLOAD_SHA256`（构建期自证），
  `build.yml` 运行时从 txt 读 URL/sha。**别再把 pin 写进 workflow**：`GITHUB_TOKEN` 是 GitHub App
  token、没有 `workflows` 权限，改动一旦涉及 `.github/workflows/**`，push 会被硬拒
  （`refusing to allow a GitHub App to create or update workflow … without workflows permission`），
  表现为「载荷发好了、pin 改了、最后一步红了、pin 永远落不了地」（2026-11-02 跟 3.0.3 实录）。

### 重建载荷（两条路线，都验证过）

**路线 A（本次采用）：从在役实机取** —— 实机已经 OTA 到最新版，取到的就是 arm64 真件：

```bash
ssh root@<在役实机> 'tar czf /tmp/roceos-tree.tar.gz -C /opt --exclude="roceos/data" --exclude="roceos/logs" roceos'
scp root@<在役实机>:/tmp/roceos-tree.tar.gz .
```

**路线 B：从官方固件镜像取**（镜像里是发布时的版本，可能落后于 OTA）：

```bash
xz -dc <官方 img.xz> > ref.img          # 约 4.0GiB
# Linux 上：losetup -Pf --show ref.img → mount -o ro <loop>p2 /mnt/ref → /mnt/ref/opt/roceos
# Windows 上：用仓库脚本 tools/…/ext4 只读解析（或用任意 ext4 读取工具）读 /opt/roceos
```

### 打包规则（payload v2 实证）

1. 以 **payload v1 为骨架**（它含 `opt/roceos-ai/`、`etc/nginx/{sites-available,ssl}`、
   `etc/systemd/system/roceos*.service`、`lib/firmware/aic8800/`、`usr/lib/python3/dist-packages/`）；
2. 删掉骨架里的 `opt/roceos`，换成路线 A/B 取到的**整棵树**（`data/`、`logs/` 必须排除）；
3. 确定性打包（成员排序、mtime/uid/gid 归零）→ `roceos-payload.tar.gz`（v2 = 88.1 MiB）；
4. 发 release（tag `roceos-payload-v2`，仓库用**本仓** linyueweia/lyw-hh）→ 拿到 sha256。

### 判据（缺一不可）

```bash
# ① 载荷里的 roceos 与官方件逐字节一致（本次 = 实机 8c96b9e7…）
tar -xzOf roceos-payload.tar.gz ./opt/roceos/roceos | sha256sum
# ② version.json 在位且是目标版本
tar -xzOf roceos-payload.tar.gz ./opt/roceos/version.json
# ③ data/ 与 logs/ 没被打进去（打进去 = 把别人家的数据库带到新机器上）
tar -tzf roceos-payload.tar.gz | grep -E 'opt/roceos/(data|logs)' && echo 失败 || echo 干净
```

### 版本一变要同步改的三处（少一处就静默用旧件）

1. `official-roceos.txt` 的 `version:` / `payload_sha256:`；
2. 扩展 `extensions/*-roceos.sh` 的 `ROCEOS_PAYLOAD_SHA256`；
3. workflow `build.yml` 里 `curl` 之后那行 `sha256sum -c` 的期望值（与 (2) 同值）。

改完 push 会触发整机重建（约 1.5~2 小时），产物自证里 roceos 段会核对落盘件。
